# Luotopia 服务端架构讨论结果

## 一、总体定位

Luotopia Server 采用 Go 语言开发，目标是为现有 Flutter 客户端提供长期稳定的服务端架构框架。

服务端采用“模块化单体”形态：部署上是一个服务进程，内部按业务模块划清边界。这样可以降低早期部署和协作复杂度，同时保留后续按模块拆分服务的可能性。

当前服务端主要承载：

- Luotopia 自有账号体系
- 用户数据同步
- 运营内容与信息推送
- 脚本热更新
- 全校课表
- 课程给分
- 课程评价
- 论坛
- 学习资料共享
- 天气代理
- 后台管理与内容治理

服务端不承载、不保存、不代理武汉大学统一认证个人凭据，也不处理个人教务 Cookie、Token、个人成绩、个人课表或预约状态。所有 WHU 个人认证相关能力继续由客户端本地处理。

## 二、核心架构原则

### 1. 模块化单体

服务端初期不拆微服务。所有业务模块运行在同一个 Go 服务中，但模块之间通过清晰接口协作，不直接跨模块访问内部实现或数据库表。

这种方式适合当前阶段：

- 部署简单
- 调试成本低
- 模块边界仍然清楚
- 后续可按模块拆分

### 2. 业务模块按领域划分

服务端业务代码放在 `internal/modules/<module>` 下。每个模块使用统一的四层结构：

- `domain`：业务概念、领域规则、领域接口
- `app`：业务流程编排
- `infra`：数据库、缓存、外部服务等技术适配
- `transport`：HTTP 等外部入口

四层含义可以简单理解为：

- `domain` 回答“这个业务是什么”
- `app` 回答“这个业务流程怎么走”
- `infra` 回答“它具体怎么存、怎么调外部系统”
- `transport` 回答“外部请求怎么进入这个模块”

### 3. 平台能力统一放置

跨模块基础设施统一放在 `internal/platform`，包括：

- 配置加载
- PostgreSQL 连接
- Redis/cache 适配
- 对象存储适配
- HTTP 框架与中间件
- 日志、错误响应、请求 ID
- 审计事件
- 后台任务调度

业务模块不各自实现这些横向能力。

## 三、模块边界

### auth

`auth` 只负责 Luotopia 自有身份认证和会话。

账号体系采用“用户主体 + 多登录凭证”的模型。手机号、邮箱、密码、第三方身份都不是账户本体，而是绑定在同一个用户主体上的登录凭证。

已确定方向：

- Luotopia 账号与 WHU 账号完全并行、互不耦合
- 支持手机号、邮箱、密码相关登录能力
- 不使用公开用户号作为登录标识
- 登录态采用短期访问凭证 + 长期刷新凭证
- 刷新凭证绑定服务端会话记录，可撤销、可轮换

### profile

`profile` 负责用户公开资料，例如昵称、头像、公开用户号。

登录凭据和公开资料分离。论坛、评价、资料共享等业务只读取公开资料，不读取手机号、邮箱等认证信息。

### access

`access` 负责角色、权限和授权判断。

`auth` 负责“你是谁”，`access` 负责“你能做什么”。后台管理、内容治理、热更新发布、课表导入等都通过 `access` 判断权限。

### sync

`sync` 负责客户端用户数据同步。

首阶段同步范围：

- 日程事项
- 课程表元数据
- 必要课程实例数据

不同步：

- 个人成绩单
- WHU Cookie 或 Token
- AI API Key
- AI 系统提示词
- 其它敏感本地配置

同步策略采用“版本号 + 服务端仲裁”。服务端保存记录版本，客户端上传时携带基于的版本；版本冲突时由服务端返回冲突状态，不静默覆盖。

### course

`course` 是课程相关业务的共享核心。

全校课表、课程给分、课程评价、学习资料共享都围绕课程组织，但不应各自维护互不兼容的课程概念。`course` 提供共享课程主数据边界，具体标识和匹配策略后续再细化。

### timetable

`timetable` 负责全校课表。

全校课表数据首选通过管理员导入维护，而不是服务端抓取个人教务数据，也不是从用户个人课表聚合。

该模块负责：

- 全校课表数据导入边界
- 数据版本
- 查询能力
- 客户端缓存对接边界

### grading

`grading` 负责课程给分。

服务端不保存用户个人成绩单，只接收用户主动提交的匿名给分样本，并提供聚合统计结果。

该模块和 `review` 分开，因为给分是结构化数据和统计问题，而课程评价是社区内容问题。

### review

`review` 负责课程评价。

它处理课程评分、文字评价、标签、点赞、举报入口等评价社区能力。课程评价强绑定 `course`，但不并入 `course`，避免课程主数据模块膨胀。

匿名评价能力放在 `review` 模块内部实现。匿名不等于无账号，服务端仍需要能进行反滥用和治理追溯。

### forum

`forum` 负责珞珈防空洞论坛。

论坛和课程评价分开。二者都可以共享 `profile` 与 `moderation`，但业务模型不同，不合并为一个泛化 community 模块。

### material

`material` 负责学习资料共享。

该模块管理资料业务本身，包括资料元数据、上传/下载语义、课程关联等。

相关能力通过其它模块协作：

- 文件对象走 `platform/storage`
- 课程关联走 `course`
- 审核举报走 `moderation`
- 登录身份走 `auth`
- 展示资料走 `profile`

### moderation

`moderation` 负责公共内容治理能力。

论坛帖子、课程评价、资料上传等都是可治理对象。举报、审核、隐藏、审计等通用流程不在各业务模块重复实现。

业务模块保留自己的内容模型，`moderation` 只处理通用治理状态和流程。

### content

`content` 是运营内容中心。

它承载面向用户展示的服务端驱动内容，例如：

- 设置页服务器头图
- 活动卡片
- 公告
- 版本提示
- 校园页运营信息

用户提到的“信息推送”在架构上归入运营内容中心，而不是其它业务模块的通知底座。

### hot_update

`hot_update` 负责脚本热更新。

客户端当前已有热更新模型，会拉取脚本 manifest 和脚本文件。服务端后续应承载脚本版本、发布、灰度、回滚、安全校验等边界。

热更新不并入 `content`，因为它不是给用户看的运营内容，而是客户端运行时能力。

### weather

`weather` 负责天气数据代理。

天气模块独立于运营内容中心。它负责代理外部天气接口，避免客户端暴露第三方 API Key，并为客户端提供天气展示所需数据。

### admin

`admin` 是后台管理入口编排层。

它不吞掉业务逻辑，只负责管理侧入口、权限校验和调用各业务模块。例如：

- 课表导入调用 `timetable`
- 热更新发布调用 `hot_update`
- 运营内容发布调用 `content`
- 举报审核调用 `moderation`

## 四、数据与基础设施

### 数据库

主数据库选择 PostgreSQL。

采用单数据库模式，但模块拥有自己的表和迁移。跨模块协作通过模块接口完成，不直接读取其它模块的数据表。

### 缓存与临时状态

预留 Redis 适配。

Redis 可用于：

- 验证码
- 限流
- 会话临时状态
- 天气缓存
- 热更新发布状态

### 文件与对象存储

通过 `platform/storage` 抽象文件存储。

资料、头像、头图、脚本等都不直接绑定本地磁盘实现。开发环境可以使用本地存储，生产环境可切换到 S3 兼容对象存储。

### 后台任务

后台任务采用 `platform/jobs` 调度，业务模块注册自己的任务。

调度框架负责生命周期、日志、错误处理和关闭流程；业务模块只负责自身任务语义。

### 观测与审计

日志、请求 ID、错误响应、审计事件统一由 `platform` 提供。

业务模块只上报结构化业务事件，不各自定义日志和审计格式。

## 五、API 与客户端边界

### API 入口

服务端保持一个进程，但 API 入口分为：

- 客户端 API
- 管理后台 API
- 健康检查等基础入口

客户端 API 和管理 API 分路由组，权限、限流、审计边界分开。

### API 契约

预留 OpenAPI 契约目录。

后续客户端重写 Luotopia 账号、同步、热更新和运营内容接入时，应以版本化 OpenAPI 契约为准。

### 客户端隐私边界

客户端以后接入服务端时必须遵守：

- 旧 Luotopia 账号实现会删除重写
- WHU 凭据不上服务端
- 个人成绩不上服务端
- AI Key 和系统提示词不上服务端
- 只同步明确允许同步的数据

## 六、服务端目录骨架

服务端顶层目录采用：

```text
Luotopia-server/
  api/
  cmd/
  configs/
  deployments/
  docs/
  internal/
```

其中：

- `cmd/server`：主服务入口
- `cmd/migrate`：迁移入口
- `api/openapi`：API 契约
- `configs`：配置模板
- `deployments`：本地开发部署配置，例如 Docker Compose
- `docs`：服务端架构与客户端接入文档
- `internal/platform`：跨模块基础设施
- `internal/modules`：业务模块

业务模块目录统一采用：

```text
internal/modules/<module>/
  domain/
  app/
  infra/
  transport/
  README.md
```

每个模块 README 使用中文说明：

- 模块职责
- 不负责什么
- 依赖哪些模块
- 对外提供什么边界

## 七、执行范围

后续执行“搭服务端架构骨架”时，允许创建可编译空服务：

- 可写最小 `main`
- 可写最小路由启动
- 可写配置加载骨架
- 可写健康检查
- 可写目录 README
- 可预留 OpenAPI、配置模板、Docker Compose

不写实际业务逻辑：

- 不实现账号注册登录
- 不实现同步协议
- 不实现论坛
- 不实现课程给分或评价
- 不实现资料上传
- 不实现热更新发布逻辑

验证范围为：

```powershell
go test ./...
```

只验证骨架可编译，不额外添加业务测试或 CI/CD。
