# 全校课表数据结构说明

本文档按当前代码实现描述 Luotopia 的“全校课表”数据结构。它覆盖客户端 `all_school_timetable` 子应用、服务端 `school_timetable` 模块、统一拉取中的全校课表同步块，以及导入包和本地缓存的结构。

这里的“全校课表”指学校教务系统公开查询到的全校开课数据，不是用户自己的个人课程表。个人课程表只在客户端本地保存；全校课表保存在服务端并以公共数据的方式同步到客户端本地缓存。

## 1. 总体模型

数据模型以**教学班（offering）为唯一核心**，星型展开：

1. **学期（term）**：例如 `2025-2026-2`。一个学期包含一批教学班、上课安排和归档源行。
2. **课程（course）**：跨学期共享的课程目录项（课程号、课程名、学分）。
3. **教师（teacher）**：跨学期共享的教师身份，ID 可扩展以区分同名教师。
4. **教学班（offering）** ★唯一核心实体★：一次实际开课班级，承载课程相关全部单值内容。
5. **教学班教师（offering_teacher）**：教学班与教师的多对多链接（主讲 / 其他），携带职称。
6. **受众（audience）**：教学班面向的年级、专业、计划学院、课程类别等约束切片。
7. **上课（meeting）**：教学班的一条上课规则（星期、节次、地点、周次），地点与周次都在此粒度。
8. **源数据行（source_row）**：教务系统原始行归档，服务端留存、不下发客户端。

这套结构故意把“课程”“教学班”“上课规则”分开。原因是教务原始表通常一行里混合了课程名、教师、班级、学生范围和多个星期几字段；拆开后客户端可以做课程搜索、教学班详情、按星期过滤、按个人课程匹配等操作。“课程头”（某课程在某学期的开课聚合）不再物化为表，而是搜索时对 offerings 按 `term_course_id` 聚合得到。

## 3. 版本与同步模型

全校课表作为公共数据通过统一拉取同步。客户端每次拉取时带上本地 `school_timetable_version`，服务端返回是否有变化，以及该走增量变更还是整包替换。

服务端版本有两种概念：

- 全局数据集版本：`school_timetable_dataset.version`。每次有实际变更的学期发布后递增。
- 学期发行版本：`school_timetable_releases.version`。落在某个具体学期上。

客户端本地只保存一个当前数据集版本：

- `school_timetable_meta['dataset_version']`
- `school_timetable_meta['dataset_checksum']`
- `school_timetable_meta['updated_at']`

同步响应中的 `school_timetable` 块包含：

- `changed`：客户端版本与服务端版本是否不同。
- `latest_version`：服务端当前全局数据集版本。
- `checksum`：当前实体集合聚合后的校验。
- `schema_version`：数据结构版本，当前为 `2`。
- `terms`：当前激活学期 key 列表。
- `sync_mode`：`changes` 或 `bundle`。
- `changes`：增量模式下的实体变更列表。
- `bundle`：整包模式下的 SQLite gzip 下载信息。
- `published_at`：数据集发布时间。
- `min_replayable_version`：服务端保留的最早可安全增量回放版本下界。

当客户端版本过旧、变更数量超过阈值、变更日志归档断层，或有版本变化但无可用变更时，服务端返回 `sync_mode = bundle`。客户端下载 `bundle.href` 指向的 `.sqlite.gz`，校验 `bundle.checksum` 后清空本地全校课表表并整体替换。

`sync_mode = changes` 时，客户端逐条应用 `upsert` 或 `delete`，然后重建 FTS 搜索表并推进本地版本。`source_row` 实体不进 changes 流、不进 bundle，仅服务端归档。

## 4. 服务端 Postgres 元数据层

服务端 Postgres 不保存可直接查询课程详情的规范化表。长期持久化的是“实体 KV + 变更日志 + 发行版本元数据”。

### 4.1 `school_timetable_dataset`

全局数据集头，单行，固定 `id = 1`。字段：`version`、`checksum`、`schema_version`（当前 `2`）、`min_replayable_version`、`published_at`、`updated_at`。

### 4.2 `school_timetable_releases`

学期发行版本表，主键 `(term_key, version)`。承载学期元维度（`school_year`/`term`/`first_week_monday`）、`row_count`、源/包校验、离线包定位（`bundle_*`）与 `active`。管理端学期列表读的是 active release。

### 4.3 `school_timetable_entities`

当前数据集实体表，主键 `(entity_type, entity_id)`。当前同步实体类型：`term`、`course`、`teacher`、`offering`、`offering_teacher`、`audience`、`meeting`。跨学期共享实体使用空 `term_key`，目前为 `course` 和 `teacher`。`source_row` 也写此表归档，但标记为非同步实体，不进 bundle 与 changes。

### 4.4 `school_timetable_changes`

增量同步日志表，主键 `(version, sequence)`。字段：`operation`、`entity_type`、`entity_id`、`term_key`、`payload_json`、`base_version`、`created_at`。非同步实体（`source_row`）不会出现在 changes 流里。

## 5. 实体类型与 payload

### 5.1 `term`

学期。核心字段：`term_key`、`school_year`、`term`、`school_year_code`、`term_code`、`first_week_monday`、`row_count`、`source`、`source_checksum`。客户端落表为 `school_timetable_terms`。

### 5.2 `course`

跨学期共享的课程目录项。字段：`course_no`、`course_name`、`credits`。`id = sha256("course", course_no, course_name, credits)`。客户端落表为 `school_timetable_courses`。

### 5.3 `teacher`

跨学期共享的教师身份。字段：`name`、`name_key`、`seq`。ID 采用可扩展编码 `id = sha256("teacher", name_key, seq)`，`seq` 默认 0。源数据无工号，默认按姓名合并；构建脚本读可选的覆盖表 `teacher_overrides.json`（按 `name` + 开课学院/课程号等线索）给同名教师分配独立 `seq`，从而生成不同稳定 ID，无需改 schema。客户端落表为 `school_timetable_teachers`。

### 5.4 `offering`

教学班，唯一核心实体。课程身份引用 `course_id`，教师经 `offering_teacher` 关联，地点与周次在 `meeting`。保留 `term_course_id = sha256("term_course", term_key, course_id)` 作为分组哈希，供课程头聚合与跨模块（课程给分/评价）关联。

核心字段：`course_id`、`term_course_id`、`source_key`、`teaching_class_name`、`open_college`、`college_id`、`open_dept_id`、`course_nature`、`course_category`、`open_type`、`people_raw`/`capacity`/`selected_count`、各学时（理论/上机/实验/实践）、`remark`（选课备注）、`note`（备注）、`other_teachers`、`textbook`、`publisher`、`search_text`。`search_text` 由构建时拼接，已包含该教学班全部教师姓名，支持按教师搜索。客户端落表为 `school_timetable_offerings`。

### 5.5 `offering_teacher`

教学班与教师的多对多链接。字段：`offering_id`、`teacher_id`、`role`（`main`/`other`）、`title`（职称）、`ordinal`。客户端落表为 `school_timetable_offering_teachers`。

### 5.6 `audience`

教学班面向的学生范围与课程属性条件切片。名称在 offering（展示），代码在此（筛选）。字段：`grade`/`grade_code`、`major`/`major_code`、`plan_college`、`course_nature_code`、`course_category_code`、`open_type_code`、`condition_code`。客户端落表为 `school_timetable_audiences`。

### 5.7 `meeting`

教学班的一条上课规则。地点与周次都在此粒度；周次数组折叠为 `week_indexes`（JSON 数组列），不再单列实体。字段：`weekday`、`day_field`、`segment_index`、`weekday_label`、`raw_day_text`、`raw_segment_text`、`week_text`、`section_text`、`section_start`、`section_end`、`location_text`、`week_indexes`、`parse_status`。解析痕迹字段全保留以便排错。客户端落表为 `school_timetable_meetings`。`occurrence_id` 构造为 `meeting_id:week_index`，表示某条规则在某教学周的一次发生。

### 5.8 `source_row`

原始教务行归档，供追溯排错。字段：`term_course_id`、`offering_id`、`source_key`、`package_index`、`status`、`fields`（完整原始字段 map）。服务端留档：写 `school_timetable_entities`，但不下发客户端（不进 bundle、不进 changes 流）。客户端无对应表。

## 6. 客户端 SQLite 查询层

客户端查询全校课表只查本地 SQLite 缓存，不访问服务端课程搜索接口。

本地表与实体类型的对应关系：

- `school_timetable_meta`：本地数据集版本和校验。
- `school_timetable_terms`：`term`。
- `school_timetable_courses`：`course`。
- `school_timetable_teachers`：`teacher`。
- `school_timetable_offerings`：`offering`。
- `school_timetable_offering_teachers`：`offering_teacher`。
- `school_timetable_audiences`：`audience`。
- `school_timetable_meetings`：`meeting`。
- `school_timetable_search_fts`：课程头搜索索引，不是服务端实体。

本地表没有声明外键，关联通过字符串 ID 约定完成。整包替换时清空这些业务表，再从 bundle SQLite 复制同名表；增量更新时按实体类型逐表 upsert/delete。客户端不再保留整行原始 JSON 快照（`detail_fields_json` 已移除）；有内容的原始字段都已晋升为对应表的类型列，完整原文仅服务端 `source_row` 归档。

## 7. 客户端领域模型

客户端页面映射成几个面向 UI 的模型（统一命名：Dart 用同名 camelCase 镜像全栈一致的 snake_case 列）：

- `SchoolTimetableTerm`：学期选择器。
- `AllSchoolTimetableQuery`：搜条件（`termKey`/`keyword`/`mode`/`openCollege`/`grade`/`major`/`weekday`/`building`）。
- `SchoolCourseHead`：搜索结果中的课程头，来自 offerings 按 `term_course_id` 聚合；`teachingClassCount`/`teacherSummary`/`weekdaySummary` 查询时聚合得到。字段 `courseId`（原 `catalogId`）。
- `SchoolTeachingClass`：教学班详情条目。`instructor`/`title` 来自 `offering_teacher→teacher` 聚合；`grade`/`major`/`planCollege` 来自 audiences 聚合；`scheduleSummary`/`weekdaySummary` 来自 meetings 聚合。字段 `courseId`（原 `catalogId`）。
- `SchoolClassMeeting`：上课规则展示数据，含 `weekIndexes`（原独立 `meeting_week` 表折叠而来）；删除了恒空的 `building`/`room`。
- `PersonalCourseMatchQuery` / `CourseEntityLink`：个人课程到全校实体的映射。链接输出 `termCourseId`/`offeringId`/`teacherId`/`occurrenceId`（`teacherId` 原 `instructorCourseId`，语义改为存教师 ID）。

个人课程详情 `ItemCourseDetails` 已预留 `termCourseId`/`offeringId`/`teacherId`/`occurrenceId`，使后续课程给分、评价、学习资料模块可从个人课程跳到全校实体。

## 8. 搜索与筛选

课程搜索以 `school_timetable_offerings` 为主表，`GROUP BY term_course_id` 聚合成课程头。关键词搜索同时使用 `school_timetable_search_fts` 的 FTS5 命中 offerings 与多个 LIKE 模糊匹配（含 `search_text`，已带教师姓名，覆盖中文子串搜索）。排序按精确/前缀/包含/其他分级，再按教学班数与课程名。

专业模式筛选通过 `EXISTS` 子查询把课程头限制到至少有一个教学班满足开课学院/年级/专业/星期/楼栋条件。FTS 表由 offerings 经 join 重建，整包与增量写入后都重建。

## 9. 导入包与整包缓存

管理端上传单学期 `.sqlite.gz`，服务端 `ParsePackage` 解压为临时 SQLite 并要求恰好一个学期。导入包需含与客户端缓存同名的核心表：`school_timetable_terms / courses / teachers / offerings / offering_teachers / audiences / meetings`（外加服务端归档的 `source_rows`）。

发布成功后服务端据全部当前同步实体重新生成全局 bundle SQLite gzip，可含多个激活学期。客户端整包替换流程：下载并校验 gzip → 解压为 SQLite → ATTACH → 清空本地业务表并按同名表复制 → 重建 FTS → 写 meta → DETACH。

## 10. 命名与字段映射

- `catalog_id` → `course_id`（全栈统一）。
- `instructor_course` / `instructor_id` → 由 `teacher` / `teacher_id` + `offering_teacher` 取代。
- `meeting_rule` / `meeting_week` → `meeting`（周次折叠进 `week_indexes` 列）。
- `source_status` → `status`。
- 表名统一复数：`school_timetable_terms / courses / teachers / offerings / offering_teachers / audiences / meetings`（+ 服务端 `source_rows`）。

## 11. 一张关系图的文字版

从查询角度：

```
school_timetable_terms.term_key
→ school_timetable_offerings.term_key
→ school_timetable_offerings.course_id = school_timetable_courses.id
→ school_timetable_offering_teachers.offering_id = school_timetable_offerings.id
→ school_timetable_offering_teachers.teacher_id = school_timetable_teachers.id
→ school_timetable_audiences.offering_id = school_timetable_offerings.id
→ school_timetable_meetings.offering_id = school_timetable_offerings.id
（school_timetable_source_rows 仅服务端，指回可追溯源行归属）
```

从同步角度：`school_timetable_entities` → 按导入前后差异生成 `school_timetable_changes`（排除 source_row）→ 更新 `school_timetable_dataset` → 写某学期 active `school_timetable_releases` → 生成全局 bundle（排除 source_row）→ 客户端 apply changes 或 replace bundle → 客户端本地表供全校课表页面查询。
