# 数据库设计主要问题

## 结论

全校课表 SQLite 快照的核心实体应从“整段上课规则”改为“课程实例”。

这里的课程实例不是某个具体日期的一次上课，而是从 `周日` 到 `周六` 字段中切分出来的一段独立排课安排。它表达：

```text
星期几 + 一组教学周 + 一段连续节次 + 地点原文
```

例如：

```text
1-16周6-8节1区5-306,11-13周9节1区5-306
```

应切成两个课程实例：

```text
课程实例 1：第 1 到第 16 周，6-8 节，地点 1区5-306
课程实例 2：第 11 到第 13 周，9-9 节，地点 1区5-306
```

第一个实例不是 16 个按日期展开的记录，也不是 `16 * 3` 个逐节记录。它就是一条跨多个教学周重复发生的连续上课安排。

## 现有设计风险

### 1. 源字段不能整体当成一条规则

全校课表的星期字段经常包含多个逗号分隔片段。如果把整个星期字段合成一条 rule，再把所有周次和所有节次分别展开，会丢失周次、节次、地点之间的对应关系。

错误模型会把：

```text
1-16周6-8节A地点,11-13周9节B地点
```

误解成：

```text
1-16周 + 11-13周
6-8节 + 9节
A地点 + B地点
```

这会制造不存在的组合。

### 2. `key` 和 `jxbmc` 都不能作为教学班主键

真实样本中，源系统隐藏字段 `key` 有重复，也有空值。同一个 `jxbmc` 也可能因为年级、专业、计划学院、课程性质等字段不同出现多行。

教学班主键应使用结构化 stable id，至少包含：

```text
学期 + 课程号 + 教学班名 + 教师 + 排课签名
```

源 `key` 只作为原始字段保存。

### 3. 地点暂不适合结构化

当前样本里的地点文本包含教学楼、操场、体育馆、虚拟教室、容量括号和其他备注。第一阶段如果强行拆成教学楼和教室，错误率会影响主路径。

因此地点只保留 `location_text` 原文，不建立地点维表，不让地点结构化结果参与主键或核心查询。

### 4. 按日期展开的 occurrence 不作为核心表

按 `first_week_monday` 展开到具体日期可以服务日历视图，但它不是第一阶段的核心实体。

原因是：

- 数据量会显著增加。
- 日期依赖校历和第一周周一，属于派生信息。
- 当前全校课表匹配更关心教学周、星期和节次范围。

如果将来需要日程提醒，可以由课程实例临时推导出具体日期上的日历发生项。

## 推荐实体结构

### 课程目录

表示“这是什么课”。

主要字段：

- 内部整数主键
- stable id
- 课程号
- 课程名
- 规范化课程名
- 学分

课程目录不保存学期、教师、上课时间和地点。

### 学期课程

表示“这门课在某个学期开出”。

主要字段：

- 内部整数主键
- stable id
- 学期
- 课程目录引用

它用于全校课表搜索聚合和课程详情入口。

### 教学班

表示“某学期某门课由哪些老师、以哪个教学班、按哪组安排开出”。

主要字段：

- 内部整数主键
- stable id
- 学期课程引用
- 课程目录引用
- 学期
- 课程号、课程名快照
- 教学班名
- 教师名
- 其他教师
- 开课学院
- 课程性质、课程类别、开课类型
- 容量、已选人数
- 学时信息
- 教材、出版社、备注
- 源系统 key
- 原始字段 JSON

教学班是全校课表客户端展示和搜索结果的主要对象。

### 面向对象

表示一个教学班面向的年级、专业、计划学院等切片。

主要字段：

- 内部整数主键
- stable id
- 教学班引用
- 年级
- 专业
- 计划学院
- 课程性质
- 课程类别
- 开课类型
- 源行号

这样同一实际课堂不会因为多个培养方案切片而在搜索结果里重复展示。

### 课程实例

表示一个教学班的一段独立排课安排。

主要字段：

- 内部整数主键
- stable id
- 教学班引用
- 学期课程引用
- 课程目录引用
- 学期
- 星期几
- 星期字段名
- 片段序号
- 原始星期字段全文
- 当前片段原文
- 开始节次
- 结束节次
- 地点原文
- 解析状态

课程实例的 stable id 应基于结构化输入生成：

```text
course_instance
教学班 stable id
星期几
片段序号
周次集合
开始节次
结束节次
规范化地点原文
```

这里不使用具体日期，因为课程实例不是按日期展开的实体。

### 课程实例周次

表示一个课程实例覆盖哪些教学周。

主要字段：

- 课程实例引用
- 教学周序号

一个课程实例可以对应多个周次，例如第 1 到第 16 周。这个表让单双周、范围周和离散周都能统一表达。

### 源行归档

保存全校课表原始 HTML 行，用于排查和重新导入。

主要字段：

- 内部整数主键
- 学期
- 包内行号
- 源系统 key
- 关联教学班
- 原始字段 JSON
- 导入状态
- 错误信息

客户端常规查询不依赖这张表。

### 搜索索引

全校课表搜索不应依赖 `%keyword% LIKE` 扫描。SQLite 快照应内置 FTS 索引。

搜索文本建议包含：

- 课程号
- 课程名
- 教学班名
- 教师名
- 开课学院
- 年级、专业摘要

FTS 命中后回表读取教学班、课程目录和课程实例。

## 查询方式

### 全校课表搜索

先查搜索索引，得到教学班候选，再加载：

- 课程目录
- 学期课程
- 教学班
- 面向对象摘要
- 课程实例列表

列表页展示教学班，详情页展示该教学班下的课程实例。

### 个人课表匹配

个人课表导入项通常有：

```text
学期、课程名、教师、教学周、星期几、节次范围、地点文本
```

匹配全校快照时，优先按课程实例筛选：

```text
学期相同
星期几相同
教学周命中
节次范围相同或相交
```

再结合课程名、课程号、教师名、教学班名和地点原文做弱匹配。

### 日历日期推导

如果页面需要具体日期，不单独查 occurrence 表，而是用：

```text
first_week_monday + week_index + weekday
```

从课程实例临时计算。这个结果可以在客户端内存中使用，不作为第一阶段核心数据库表。

## 推荐表命名

建议当前阶段保留以下核心表：

```text
course_catalog_rows
term_course_rows
course_offering_rows
course_audience_rows
course_instance_rows
course_instance_week_rows
course_source_rows
course_search_fts
artifact_metadata_rows
```

暂不建立：

```text
course_occurrence_rows
location_building_rows
location_room_rows
```

## 性能要点

- artifact 内部关系键使用 `INTEGER PRIMARY KEY`，外部稳定引用使用 `stable_id TEXT UNIQUE`。
- 课程实例按 `term_key + weekday + section_start + section_end` 建索引。
- 课程实例周次按 `instance_id + week_index` 建联合主键。
- 搜索走 FTS，不走 `%keyword% LIKE`。
- 详情页按教学班一次性加载课程实例，避免 N+1 查询。
- 地点只保存原文，避免地点解析错误污染主查询。

## 第一阶段取舍

第一阶段只解决课程身份、教学班聚合、排课字段切分和客户端快照查询。

不做：

- 旧 SQLite 兼容迁移
- 地点结构化
- 具体日期 occurrence 持久化
- 完整校历服务
- 课程评价和给分统计

这样数据库主模型会更小，也更贴近当前用户对“课程实例”的定义。
