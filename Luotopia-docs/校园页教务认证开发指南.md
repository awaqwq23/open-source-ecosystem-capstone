# 校园页教务认证开发指南

本文面向继续开发校园页次级应用的社区贡献者，说明如何接入现有武汉大学统一认证和教务系统授权能力。

## 基本结构

项目采用轻量 `MVVM + feature-first` 结构。
校园页应用主要位于 `lib/features/pages/campus/`，
武汉大学认证能力位于 `lib/features/whu_auth/`，
课程导入这类可复用功能位于 `lib/features/components/`。

要求开发新校园应用时保持依赖方向清楚：页面和 ViewModel 负责交互与状态，domain 负责模型和规则，data 负责请求、解析与外部服务对接。

## 教务认证怎么复用

新应用不需要自己处理 CAS Cookie，也不应该复制 WebView 登录、Cookie 读取、重定向和会话维护逻辑。这些已经由 `whu_auth` 模块封装。

开发者只需要理解三件事：

1. 用户在“武大教务账户”页面通过内嵌 WebView 登录武汉大学统一认证。
2. 登录成功后，应用保存统一认证 Cookie，并能用它换取教务系统会话。
3. 校园页应用在真正请求教务接口前，通过认证网关获取一个已授权的教务会话，使用完必须关闭。

页面层应先判断用户是否已认证。未认证时展示登录引导，入口指向现有武大教务账户页；已认证时再请求教务系统。data 层服务只接收已授权会话并负责请求接口，不直接依赖页面上下文。

## 查询型应用

查询型应用的特点是只从云端单向获取信息，并在需要时持久化到本地；它不向云端提交业务写操作。当前“成绩”和“课程表”都属于这一类。

“成绩”是最直接的查询型参考：它从校园页宫格进入成绩页，页面检查武大认证状态，认证通过后获取教务会话，再由成绩服务请求教务成绩接口，最后把返回结果解析为页面需要的成绩模型。

“课程表”也是查询型应用，但它比成绩多一步本地持久化：它获取教务会话后请求个人课表接口，再把教务数据转换为本地课程表和课程事项，供主页、列表页等其他模块复用。它不改变教务系统中的远端数据。

开发查询型应用时，重点是把云端数据稳定地转换为本应用自己的模型：

- 校园页只负责入口和跳转。
- 页面负责未登录、加载中、错误、空数据和成功展示。
- data service 负责访问教务接口并解析原始返回。
- 如果数据只在当前页面展示，模型可以留在校园页模块内。
- 如果数据要被主页、列表页、AI 或桌面小组件复用，应转换为 shared 中的共享实体或仓储数据。
- 页面不直接拼接复杂请求，也不直接解析教务返回的原始数据。

空闲教室、全校课表、成绩、课程表、学习资料列表等，只要不向远端提交业务变更，都应优先按查询型应用设计。

## 交互型应用

交互型应用的特点是会与云端发生双向业务交互，不只是读取信息，还会提交预约、续借、取消、确认、支付等会改变远端状态的操作。座位预约、图书借阅、运动场馆预约、E 卡付款码等都应按交互型应用设计。

开发交互型应用时，不能只考虑“请求成功后展示结果”，还要把远端状态变化当作核心业务来设计：

- 页面必须清楚展示当前远端状态，以及用户即将提交的操作会造成什么后果。
- 对预约、取消、续借、支付这类动作，提交前应有明确确认或足够清晰的操作语义。
- data service 应把“查询当前状态”和“提交业务动作”分成清晰的方法，不要混在同一个模糊接口里。
- 提交动作完成后，应重新拉取远端状态，避免只依赖本地乐观状态。
- 如果操作失败，应保留用户可理解的失败原因，并允许重试或返回安全状态。
- 对可能重复提交的动作，要考虑按钮禁用、加载态和重复点击保护。
- 不要在没有确认远端成功的情况下，把本地状态永久写成成功。

交互型应用通常需要比查询型应用更明确的 ViewModel 状态设计。至少要区分：初始加载、可操作、提交中、提交成功后刷新、提交失败、认证失效。这样页面不会在远端状态不确定时误导用户。

## 新校园应用的开发顺序

开发一个新校园应用时，建议按这个顺序做：

1. 确认它是否需要武大统一认证或教务系统授权。
2. 在校园页宫格中增加入口，并在路由表中增加页面路由。
3. 为页面设计最小 domain model，先明确页面需要展示什么数据。
4. 如果需要访问教务系统，新增独立 data service，由它负责请求、提交动作和解析。
5. 页面或 ViewModel 调用认证网关获取教务会话，再调用 data service。
6. 处理未登录、加载中、空数据、错误、成功这几类状态。
7. 如果数据需要被其他模块使用，再写入 `shared` 仓储或抽成共享模型。

不要一开始就把所有逻辑写在页面里。页面里混入认证、请求、解析和业务转换后，后续会很难维护，也不符合本项目的 MVVM 约束。

## 错误处理原则

教务系统相关功能至少要考虑这些失败情况：

- 用户尚未登录统一认证。
- CAS Cookie 已过期，教务服务授权失败。
- 教务接口返回非成功状态。
- 教务系统返回登录页、异常页或非预期格式。
- 接口字段变化导致解析失败。

错误信息应该面向用户可理解。未登录时引导登录；授权失败时提示重新登录或重试；接口失败时说明请求失败；解析失败时说明教务返回格式异常。不要静默吞掉错误，也不要在日志或界面暴露 Cookie 等敏感信息。

## 协作约定

新增校园页应用前，先检查现有 `whu_auth`、`campus/data`、`course_import` 中是否已有可复用能力。认证和教务会话必须复用现有封装，不要重复实现。

新增功能应保持一个完整闭环：校园页入口、路由、页面、数据服务、模型和错误状态要一起完成。若只是先放入口，可以保留“功能开发中”的提示；一旦接入真实服务，就应补齐页面状态和数据边界。

提交前重点自查：是否遵守 MVVM，是否复用认证网关，是否关闭教务会话，是否没有泄露敏感信息，是否将实际功能与令牌认证充分解耦。
