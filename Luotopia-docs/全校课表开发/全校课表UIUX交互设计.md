# 全校课表 UI/UX 交互设计

本文记录“全校课表”客户端子应用当前已确认的界面交互框架。本文只讨论查询工具本身，不覆盖“蹭课”“选课推荐”的交互，也不展开服务端抓取、后台上传和同步实现。

## 功能定位

“全校课表”子应用首版只做查询工具。

它的目标是让用户在竖屏手机上高性能、低负担、符合心流地查询全校课程信息。用户可以通过课程名、课程号、教师、学院、时间、地点等条件找到课程，再进入统一的课程详情页查看该课程下的教学班信息。

本子应用只查询本地已同步的全校课表数据，不要求用户登录教务系统，不直接访问教务网页。

## 页面层级

全校课表客户端只有两级核心页面：

1. 全校课表首页
2. 课程详情页

首页负责搜索、筛选、展示课程结果列表。详情页负责展示一门课的完整信息和它包含的所有教学班。

无论用户从轻量查询还是专业查询进入，点击搜索结果后都进入同一个课程详情页。轻量查询和专业查询只影响首页的筛选方式，不影响结果对象和详情页结构。

## 查询模式

首页提供两种查询模式：

- 轻量查询
- 专业查询

两种模式共享同一个搜索词。用户在轻量查询中输入关键词后，切换到专业查询时仍保留关键词，并可以继续添加精确筛选条件。

### 轻量查询

轻量查询面向普通用户的快速查找场景，默认进入此模式。

轻量模式应尽量自动推导可确定条件：

- 学期默认选择本学期。
- 学生年级默认选择用户所在年级。
- 如果没有用户资料，则不启用年级默认筛选。
- 专业可以作为后续推荐筛选，但不建议默认强筛，避免漏掉通识课、跨专业课和旁听场景。
- 学院、时间、地点默认不筛选。

默认推导出的条件必须以 chip 形式明确展示，例如“本学期”“2024级”，并允许用户一键移除。

轻量模式只暴露少量快捷筛选：

- 学期
- 年级
- 时间
- 地点
- 学院

轻量筛选使用底部选择器，不进入完整筛选页，保持查询动作快速。

### 专业查询

专业查询面向需要精确筛选课程集合的用户。

专业模式首页仍保持简洁，只展示：

- 搜索框
- 筛选按钮
- 已选筛选条件 chips
- 课程结果列表

复杂条件全部进入全屏筛选页，避免在竖屏手机首页堆叠表单。

专业筛选页按字段类型分组：

- 基础：学年学期、课程名称、课程号、教学班、教师。
- 归属：开课学院、计划学院、年级、专业。
- 时间地点：周几、节次、周次、校区或区域、教学楼、教室关键词。
- 课程属性：学分范围、课程性质、课程类别名称、开课类型。
- 容量与资料：上课人数范围、教材名称、出版社、选课备注。

筛选页底部固定操作栏：

- 清空
- 预计结果数
- 查看结果

筛选页内可以实时计算预计结果数，但不应在用户编辑筛选条件时反复刷新首页列表。用户点击“查看结果”后，筛选条件才统一应用到首页。

## 竖屏手机适配原则

竖屏手机是首要设计目标。全校课表数据天然接近表格，不能把原始字段直接搬到首页。

首页主路径应保持为：

1. 搜索
2. 扫描结果
3. 点进课程详情

首页从上到下的结构：

1. 顶部栏：返回、标题“全校课表”。
2. 数据状态：当前学期、同步状态和更新时间的紧凑提示。
3. 模式切换：轻量查询 / 专业查询。
4. 搜索框：支持课程名、课程号、教师、教室、学院等关键词。
5. 筛选 chips：横向滚动，最多占一行。
6. 结果统计：显示命中课程数量和“相关度优先”排序。
7. 单列课程结果列表。

小屏首页不展示大面积卡片，不做多列布局。结果列表应紧凑，第一屏至少能看到多门课程，让用户感知这是查询工具。

## 搜索结果列表

搜索结果始终使用单列纵向排列的紧凑行。

每一行代表一个对象：一门课。

首页不直接按教学班逐条展示。教学班信息进入课程详情页后再展示。

课程行建议控制在 2 到 3 行文本，信息优先级如下：

第一行：

- 课程名称
- 学分
- 课程属性标签，例如必修、选修、核心课程

第二行：

- 课程号
- 开课学院
- 教学班数量

第三行：

- 教师摘要，或
- 时间地点摘要，或
- 搜索命中摘要

第三行内容应根据搜索命中动态选择。用户搜教师时优先展示教师摘要；搜教室或时间时优先展示时间地点摘要；没有明显命中维度时默认展示教师摘要。

结果排序默认使用相关度优先。

## 课程详情页

课程详情页是统一详情页，不区分用户来自轻量查询还是专业查询。

详情页顶部展示紧凑课程信息：

- 课程名称
- 课程号
- 学分
- 开课学院
- 课程性质
- 课程类别名称
- 开课类型
- 教学班数量
- 教师数量

详情页主体展示该课程下所有教学班。

每个教学班默认展示：

- 教学班名称
- 教师
- 上课人数
- 时间地点
- 年级
- 专业

教学班可以展开查看更多字段：

- 学年
- 学期
- 计划学院
- 成绩录入老师
- 职称
- 理论、上机、实验、实践学时
- 周日到周六安排
- 选课备注
- 其他教师
- 教材名称
- 出版社

课程详情页的重点是帮助用户比较教学班，因此课程级元信息应保持紧凑，教学班列表应成为主要内容。

## 已确认的设计决策

- 首版只做“全校课表”查询工具，不做“蹭课”和“选课推荐”。
- 首页提供轻量查询和专业查询两种模式。
- 两种模式共享搜索词。
- 首页结果对象统一为“一门课”。
- 搜索结果使用单列纵向紧凑行。
- 点击任意课程结果进入统一课程详情页。
- 结果默认按相关度优先排序。
- 竖屏手机是首要适配目标。
- 专业筛选使用全屏筛选页。
- 轻量筛选使用底部选择器。

## 待继续确认的问题

- 轻量模式下，用户年级默认筛选是否只在首次进入且无搜索词时启用。
- 课程详情页内是否需要教学班局部筛选，例如只看某教师、只看某时间、只看某地点。
- 首页数据状态是否只展示当前学期，还是允许快速切换历史学期。
- 课程行第三行摘要的命中优先级细则。
- 专业筛选页各字段是否允许多选，以及多选条件之间的逻辑是并集还是交集。

## 更正：做成三级页

› 那我们做成三级页吧：
  1.搜索页，搜索出来的是满足条件的所有课头号相同的课程，包含多个老师，多个时间段的
  2.点击进去是第二级列表页，列出同一个课头号下教师、时间段的不同
  3.点进去才是我们说的格式统一的单个课程详情页

• 我同意，三级页更贴合这个表结构，也更符合手机心流。

  因为表里真正的层级不是“课程 → 详情”这么简单，而是：

  课头号 / 课程号 → 同课头下的不同教学班组合 → 单个教学班完整详情

  这样拆以后，每一级的信息量都更可控。

  三级结构

  第一级：搜索页
  对象是“课头号相同的一组课程”。

  这一页回答：
  “有没有这门课？”

  每行展示一个课程组：

- 课程名称
- 课程号 / 课头号
- 学分
- 开课学院
- 教学班数量
- 教师摘要：李小红、刘斌等 5 位
- 时间摘要：覆盖周一/周三/周五
- 属性标签：必修、核心课程、专业教育课程等

  这里不展示具体教学班细节，只帮助用户判断是不是要点进去。

  第二级：课头列表页
  对象是“同一个课头号下的不同教师、不同时间段、不同教学班”。

  这一页回答：
  “这门课有哪些可选班？”

  每行展示一个教学班摘要：

- 教师 / 其他教师
- 教学班编号
- 年级专业
- 上课人数
- 时间地点摘要
- 课程备注简写

  这里的重点是比较，不是完整字段展示。

  第三级：单个课程详情页
  对象是“一条具体教学班记录”。

  这一页回答：
  “这个班的完整信息是什么？”

  展示完整统一格式：

- 课程基础信息
- 教学班信息
- 教师信息
- 时间地点
- 人数
- 学时结构
- 周日到周六原始安排
- 备注
- 教材和出版社

  为什么三级更好

  这个结构比两级更稳，因为首页不用塞教学班信息，详情页也不会一次展示十几个班导致很长。用户每一步只做一个判断：

  1. 搜索页：找课程。
  2. 列表页：选老师/时间/班级。
  3. 详情页：看完整信息。

  这就是比较自然的用户心流。
  需要调整的点

  “课程详情页”这个名字现在容易歧义。建议命名成：

- 三级：班级详情

  或者：

- 二级：教学班列表
- 三级：教学班详情

  内部数据命名也要清楚：

- CourseGroup：按课头号/课程号聚合的一组课程。
- CourseOffering 或 TeachingClass：具体教学班。
- CourseDetail：单条教学班的完整详情。

  我建议现在确认一个关键规则：第一级聚合键到底用“课程号”还是“教学班字段里的课头号”。
  从你描述“课头号相同”来看，应该用课头号；但表结构里显式字段是 课程号 和 教学班，所以需要从数据里确认“课头号”是独立字段，
  还是从 教学班 字符串里解析出来。
