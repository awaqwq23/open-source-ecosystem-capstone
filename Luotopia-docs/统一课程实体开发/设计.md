# 全校课表数据库表设计说明

## 背景

全校课表数据不只是普通的课表行集合，而是“学期版本化的课程目录、教学班、上课时间地点、面向对象和原始行追溯”的组合。表设计需要先区分三类职责：

- 服务端主库保存规范化事实，负责导入、版本、追溯和一致性。
- 客户端 SQLite artifact 保存只读查询投影，负责离线查询和快速搜索。
- 搜索、汇总、计数等派生数据只作为投影或缓存，不作为事实源。

核心原则是：服务端主库低冗余、版本正确、事实边界清晰；客户端 artifact 可以为了查询速度保留冗余字段，但必须明确它是派生产物。

## 当前结构判断

当前代码里的自然层级基本合理：

```text
term
  release
    course_catalog
      term_course
        course_offering
          course_instance
            course_instance_week
          course_audience
    course_source_row
```

其中：

- `course_catalog` 表示跨学期的课程目录项。
- `course_term_course` 表示某学期的一门课程，是课程列表中的“课程头”。
- `course_offering` 表示具体教学班。
- `course_instance` 表示教学班的一组上课时间地点。
- `course_instance_week` 表示该上课安排覆盖的周次。
- `course_audience` 表示教学班面向的年级、专业、计划学院等对象。
- `course_source_row` 保留原始导入行和解析结果的关联。

问题不在于层级本身，而在于事实字段、查询投影字段和版本发布字段现在混在一起。

## 主要问题

### 版本边界不完整

现在 release 记录了版本、checksum、artifact 文件等元数据，但规范化事实表按 `term_key` 覆盖写入。这样会出现一个根本问题：激活旧 release 只改变 release 元数据，不会恢复该版本对应的规范化事实表内容。

如果 release 是一等概念，那么所有事实表都应该挂到 `release_id`，或者至少挂到 `(term_key, version)`。否则“历史版本激活”只能保证 artifact 指针正确，不能保证服务端查询事实正确。

### 冗余程度偏高

以下字段在多个层级重复：

- `course_no`、`course_name`、`credits` 同时出现在 catalog、term_course、instructor_course、offering。
- `term_key`、`catalog_id`、`term_course_id` 在很多子表里重复。
- `course_nature`、`course_category`、`open_type` 在 term_course、offering、audience 里重复。
- `teacher_summary`、`weekday_summary`、`search_text`、`teaching_class_count` 等汇总字段和事实字段放在同一层。
- `fields_json` 和明细列重复保存了大量来源字段。

服务端主库中，这些冗余会增加一致性维护成本。客户端 artifact 中，为了减少 join 和提高离线查询速度，可以保留一部分冗余，但它们应该被视为查询投影。

### 教师模型不稳定

当前 `course_instructor_courses` 更像“课程 + 教师组”的搜索聚合，不像稳定事实表。教师如果后续要支持检索、详情页、跨学期课程归并，建议拆成：

```text
teachers
course_offering_teachers
```

然后把“某教师教过哪些课”“某课程有哪些教师”做成派生查询或投影。

### 主库和 artifact schema 边界不清

服务端 Postgres 表、服务端生成的 SQLite artifact 表、客户端主 Drift DB 里都存在全校课表相关结构，而且字段类型和字段语义不完全一致。例如 artifact 使用 integer id 加 `stable_id`，服务端主库使用 text id；部分 summary 字段和明细字段也不完全对应。

这说明现在缺少一个明确的 canonical schema。建议以服务端主库事实表为 canonical schema，artifact 只是从 canonical schema 生成的只读投影。

## 推荐设计

### 发布层

```text
school_timetable_terms
school_timetable_releases
school_timetable_artifacts
```

建议：

- `school_timetable_terms` 只保存学期基础信息，例如 `term_key`、学年、学期、第一周周一。
- `school_timetable_releases` 保存 `(term_key, version)`、checksum、row_count、active、published_at。
- `school_timetable_artifacts` 保存 artifact 类型、schema_version、file_key、size、checksum。
- 所有事实表都应该通过 `release_id` 或 `(term_key, version)` 绑定到具体 release。

### 事实层

推荐主干：

```text
course_catalogs
course_term_courses
course_offerings
course_offering_teachers
course_audiences
course_meetings
course_meeting_weeks
course_source_rows
```

职责划分：

- `course_catalogs`：课程目录事实，例如课程号、课程名、学分。
- `course_term_courses`：某 release 下某学期的一门课程，保存开课学院、课程性质、课程类别、开课类型等学期维度事实。
- `course_offerings`：具体教学班，保存教学班名、容量、已选人数、备注、教材、来源 key、schedule hash 等教学班事实。
- `course_offering_teachers`：教学班与教师的关系，保存教师顺序、角色、职称等。
- `course_audiences`：教学班面向对象，保存年级、专业、计划学院、条件代码等。
- `course_meetings`：教学班上课安排，保存星期、节次起止、地点、原始文本、解析状态。
- `course_meeting_weeks`：上课安排覆盖周次，使用 `(meeting_id, week_index)`。
- `course_source_rows`：原始导入行，保存 `release_id`、package_index、source_key、status、fields_json、解析出的 offering_id。

### 投影层

推荐把以下内容移到投影层：

```text
course_search_fts
course_head_summary
offering_summary
teacher_course_summary
```

投影层可以保存：

- `search_text`
- `teacher_summary`
- `weekday_summary`
- `schedule_summary`
- `audience_summary`
- `teaching_class_count`
- 为客户端列表页准备的冗余字段

这些字段可以重建，不应作为唯一事实源。

## 字段冗余取舍

服务端主库中，建议减少以下冗余：

- `course_offerings` 不再重复保存 `course_no`、`course_name`、`credits`，通过 `term_course_id` 关联获得。
- `course_meetings` 不再重复保存 `term_key`、`catalog_id`，通过 `offering_id` 关联获得。
- `course_audiences` 不再重复保存课程名、课程号等课程事实。
- `search_text`、summary、count 字段从事实表移到投影表。

客户端 artifact 中，可以保留冗余：

- 为列表页和详情页保留课程名、课程号、教师摘要、时间摘要。
- 为过滤保留 `term_key`、`weekday`、`location_text` 等索引友好字段。
- 使用 integer id 优化 SQLite join，但外部链接和跨库引用必须使用 `stable_id`。

## ID 设计

建议统一两个概念：

- `id`：数据库内部主键，可以是服务端稳定 hash，也可以是 artifact 本地 integer。
- `stable_id`：跨发布物、跨客户端、跨服务端 API 的稳定标识。

客户端和 API 对外不要暴露本地 integer id。artifact 可以用 integer id 做 join，但需要保留 `stable_id` 作为外部稳定引用。

## 推荐结论

最终方案应该是混合设计：

- 服务端 canonical schema：规范化、挂 release、低冗余。
- 客户端 artifact schema：只读、可冗余、面向查询。
- 搜索和 summary：派生投影，不进入事实表。
- 原始行：完整保留，并挂到 release，用于追溯和重建。

这个方向能解决三个核心问题：版本一致性、冗余失控、服务端主库和客户端 artifact schema 漂移。
