# 统一课程实体开发

我们现在的任务是重整项目，让课程相关功能围绕同一套课程实体构建，而不是在课表、成绩、全校课表、蹭课、课程给分、课程评价里各自维护一套近似但不一致的对象。

第一阶段采用“大爆破替换”：不保留旧客户端数据库兼容，不做旧数据迁移，优先把课程身份、服务端快照、客户端本地缓存和最小详情页统一起来。

## 相关功能

### 课程表

从武汉大学教务系统里爬取用户指定学期课表。现有个人课表导入流程暂不改变，仍由用户选择学期和第一周周一，并生成日程事项。

### 表格页

点击课程展示课程事项详情页。课程事项详情页应优先展示统一课程实体引用；无法匹配全校快照时继续展示导入时已有字段。

### 成绩

展示用户成绩，并允许用户将自己的成绩匿名化上传系统分析。第一阶段只为成绩记录补充统一课程实体引用，不实现匿名上传聚合和给分统计。

### 全校课表

检索武大建立数字化系统之后所有的课程。第一阶段以服务端规范化快照为权威，客户端只同步和缓存快照，不再重复聚合源 HTML 行。

### 蹭课

根据用户专业、兴趣、日程空闲等信息为用户推荐课程。第一阶段只提供所需实体基础，不实现推荐逻辑。

### 课程给分

根据服务端数据统计教师-课程组合的历史给分数据。第一阶段只建立授课组合身份，不实现统计。

### 课程评价

允许用户上传或查询某个授课组合的评价。第一阶段只建立授课组合详情入口，不实现评价功能。

## 课程实体层级

武汉大学教务系统里的“课程”不是单一粒度。结合全校课表数据源结构和真实保存 HTML 数据，源系统至少拆成以下层级：

```text
课程目录 CourseCatalog
└── 课程项 TermCourse
    └── 教学班/排课单元 CourseOffering
        └── 面向对象/培养方案切片 CourseAudience
        └── 课程实例 CourseInstance
```

### 课程目录 CourseCatalog

课程目录是跨学期的课程集合，回答“这是什么课”。它主要由 `课程号(yskch)`、`课程名称(kcmc)`、`学分(kcxf)` 规范化标识，例如 `3200520011017 / 算法设计与分析 / 3.5 学分`。

课程目录不直接承载学期、老师、上课人数、时间地点、成绩录入等信息。

### 课程项 TermCourse

课程项是某个学期里课程目录的一次开出，回答“这门课在这个学期是否开出，以及面向当前学期有哪些教学班”。它由 `学期 + 课程目录` 标识。

课程项用于全校课表查询列表和课程目录在当前学期下的聚合展示。

### 教学班/排课单元 CourseOffering

教学班是选课和全校课表记录中的实际课堂单位，回答“某学期这门课以哪个班、哪个老师、哪组时间地点开出来”。

真实 HTML 数据已经证明：隐藏字段 `key` 不是教学班唯一主键，`教学班(jxbmc)` 也不是源行唯一主键。同一个 `key` 可能因年级或课程性质差异出现多行；同一个 `jxbmc` 会因专业、年级、计划学院、课程性质等面向对象差异拆成多行。因此教学班实体由 `学期 + 教学班名称 + 教师 + 排课签名` 规范化后生成内部稳定 ID，源 `key` 只能作为原始字段保留。

教学班包含课程快照、开课学院、成绩录入老师、职称、其他教师、上课人数、学时、排课摘要、选课备注、教材和出版社等信息。没有排课时间的真实课程也应进入教学班实体，只是不生成课程实例。

### 面向对象/培养方案切片 CourseAudience

全校课表 HTML 的一行更准确地说是“源行切片”。它可能不是一个独立教学班，而是同一个实际课堂面向不同年级、专业、计划学院、课程性质、课程类别或开课类型的切片。

这些差异进入教学班下的面向对象子表，而不是把同一实际课堂在查询列表里重复展示多次。

### 排课规则 CourseMeetingRule

排课规则这个名字容易误导：全校课表源字段里的 `周日` 到 `周六` 字段并不总是一条规则，可能由多个逗号分隔的上课片段组成。例如同一星期几可能出现“1-16周6-8节”和“11-13周9节”两段安排。第一阶段不再把整段星期字段直接建模为一个持久实体，而是先切分为课程实例。

服务端仍可在导入过程中使用临时规则对象辅助解析，但 SQLite 快照和统一课程实体语义以 `CourseInstance` 为准。

### 课程实例 CourseInstance

课程实例来自单个星期字段中可独立解释的一段文本，表达“星期几 + 一组周次 + 一段连续节次 + 地点原文”。它不是单个具体日期的上课记录，也不是单节课格子，而是一条已经从原始星期字段中切分出来的可独立上课安排。它保留：

- `raw_day_text`：完整星期字段原文，便于排查。
- `raw_segment_text`：切分后的片段原文。
- `weekday`：星期几。
- `week_indexes`：从片段中展开出的具体教学周集合。
- `section_start` / `section_end`：一次上课持续的连续节次范围。
- `location_text`：地点原文。

第一阶段不解析地点，不建立教学楼/教室维表，也不让地点结构化结果参与查询主路径。地点只作为原文文本保存和弱匹配依据。

例如 `1-16周6-8节` 是一个课程实例，表示第 1 到第 16 周的某个星期几都有一次连续的第 6 到第 8 节课，而不是生成 16 个按日期展开的实例，也不是生成 `16 * 3` 个逐节实例。`11-13周9节` 是另一个课程实例，表示第 11 到第 13 周各有一次第 9 节课。

如果未来需要日程提醒或日历视图，可以由 `CourseInstance + first_week_monday` 临时推导出具体日期上的日历发生项；但第一阶段数据库不把这些派生日期项作为核心实体持久化。

### 授课组合 InstructorCourse

授课组合是跨学期的教师-课程组合，由 `课程目录 + 规范化教师名` 标识。第一阶段不新增教师/教授实体，只保留教师名字符串。

授课组合用于承载未来课程评价和课程给分，因为同一位教师讲授同一门课程时，这些性质比单个教学班更稳定。

## 页面

第一阶段建立最小统一详情页体系：

- 课程实例详情页：作为“课程”事项类型的详情页，在表格、列表页等地方点开展示。
- 教学班详情页：在成绩、全校课表查询页面展示。
- 授课组合详情页：在课程给分、评价页面作为入口展示。
- 课程目录和课程项：先服务于全校课表查询与聚合展示，不单独做完整详情页。
